# N64 Core Development

## Target and Architecture

Implement an independent, environment-neutral N64 kernel in ESM JavaScript.
No third-party emulator code or runtime dependencies are introduced. Hardware
manuals and original research are references, not implementation sources.

The initial acceptance target is the user's local NTSC-U Super Mario 64 ROM:
SHA-256 `17ce077343c6133f8c9f2d6d6d9a4ab62c8cd2aa57c40aea1f490b4c8bb21d91`.
The ROM is external test input and must not be copied into the repository.

The kernel consists of a VR4300 interpreter, memory/MMIO bus, RCP scheduling,
controller/PIF processing, video output, and stereo audio output. RSP graphics
and audio tasks initially use high-level implementations of standard microcode
interfaces. This is explicitly not a cycle-accurate or arbitrary-microcode claim.
Boot initialization replaces PIF/IPL startup; game instructions are executed,
and game code, display lists, and samples are not patched or substituted.

## Acceptance Gates

- ROM byte-order normalization and CPU instruction/exception tests.
- Real ROM boot without ignored or silently stubbed CPU instructions.
- Title screen and controller-driven entry into an interactive game scene.
- Inspect captured rendered frames for geometry, textures, color, and layout.
- Verify sustained audio generated by game audio tasks, not synthetic tones.
- Check determinism and save/load continuation where supported.
- Run NES/SNES regression tests and browser ROM/audio sanity checks.
- Document unsupported hardware and microcode behavior explicitly.

## Progress

- Repository inspected; baseline working tree clean.
- Local ROM header identified: 8 MiB, big-endian `.z64`, entry `0x80246000`.
- Independent VR4300, RCP bus, Fast3D renderer, ABI1 audio, and controller paths implemented.
- The unmodified reference ROM boots into the title, file selection, opening, and courtyard.
- Scripted A-button input raises Mario from ground Y=260 to Y=372.5; analog input changes world Z by more than 1,900 units. These addresses are read by the test only, never patched by the core.
- Ten one-second gameplay audio windows contain nonzero stereo output with RMS between 0.052 and 0.124. The measured clipping fraction is zero. This is signal validation, not a claim of bit-exact audio or a subjective listening test.
- A 20-frame replay from an in-game snapshot compares the full mutable state and all emitted stereo samples, not just frame counters.
- Rendered PNGs have been visually inspected for the logo, title, menus, castle, Mario, walking, and jumping. Clearing artifacts found during inspection were fixed.
- Browser ROM loading and user-gesture startup work. N64 runs in a Web Worker with audio-consumption backpressure; AudioWorklet handles stereo playback independently of UI rendering. Busy scenes still run below real time on the development host and cause measured audio underruns; this is a known limitation, not a passed real-time/audio-quality gate.
- After dismissing the courtyard tutorial, an observed playback window delivered 1,919,616 stereo frames (about 43 seconds at 44.1 kHz), with 1,918,744 nonzero frames, peak amplitude 0.666, and zero underruns. The UI showed approximately 60 FPS. Keyboard-driven jumping was visually verified. These measurements do not establish bit-exact or subjectively verified audio quality.
- NES and SNES browser playback both deliver nonzero PCM to the AudioWorklet with no underruns in the observed regression sessions. Short keyboard taps are latched across controller polling and Start focuses the game canvas.
- The optimized 4,300-frame headless scenario completed in approximately 60 seconds on the development host. This is a measured reference run, not a cross-platform performance guarantee.
- Final regression: 46 tests passed; NES, SNES, and N64 smoke scenarios passed. The N64 scenario also checks full-state and stereo replay. Browser entry points, worker modules, and the AudioWorklet module returned HTTP 200.

## Reproduce

```bash
N64_ROM='/path/to/Super Mario 64 (U).z64' npm run smoke:n64
```

The scenario writes `tmp/n64/verification/report.json`, ten screenshots, and
`courtyard-stereo.wav`. It asserts scene diversity, actual player coordinates,
sustained unclipped stereo PCM, and save/load replay. It does not merely count
frames or accept any nonzero transient as proof of successful execution.

For an early boot failure, `node src/cli/debug-n64.mjs <rom> [frames]` writes a
CPU trace, task descriptor, RDRAM/SP dumps, and a PPM under `tmp/n64/`. These
artifacts contain cartridge-derived data and remain ignored by Git.

## Current Limits

- HLE post-IPL boot; no general PIF/CIC boot-ROM execution.
- VR4300 interpreter with simplified timing and coherent memory instead of hardware caches. Precise floating-point flags, traps, and denormal handling need further work.
- RSP Fast3D and ABI1 tasks only. No arbitrary RSP microcode or direct RDP triangle-command execution.
- Software rasterizer with nearest texture sampling, approximate blending and floating-point depth. No hardware coverage/antialiasing, exact fog, or VI reconstruction filters.
- Fixed 320x240 scanout; PAL timing is wired but not validated with a PAL game.
- ABI1 envelope ramps are a high-level implementation; the pole filter is unsupported. AI uses linear resampling to the host rate.
- Save states carry all mutable core data, including HLE audio envelopes. EEPROM persists across reset, but external save-file management is not yet exposed in the GUI.
- CPU-only rendering is not guaranteed to sustain real time on all hosts. Worker isolation and AudioWorklet avoid UI/callback contention but cannot compensate for insufficient emulation throughput.
